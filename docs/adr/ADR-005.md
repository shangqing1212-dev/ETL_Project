# ADR-005: DWD 事实表用自然键作主键,代理键仅用于 SCD2 维表

- **状态**: 已接受
- **日期**: 2026-09-17

## 背景

M4 计划草稿提出 DWD 层"代理键 + 自然键唯一索引"。实现前重新评估:本项目 DWD 是 **ODS 的派生重算层**(可全量重放),主键选择必须服务 upsert 幂等性,而 `AUTO_INCREMENT` 代理键与"可重放"原则存在根本冲突。

## 决策

1. **DWD 事实表**(dwd_orders / dwd_order_items)主键直接用自然键 `(shop_id, order_id)` / `(shop_id, order_id, item_id)`:
   - 代理键值依赖插入历史,同窗口重放不保证生成相同 key;自然键来自源端,天然重放稳定;
   - 事实表间关联(DWD→DWS)全部按自然键 join,代理键不带来 join 收益;
   - upsert 语义(ADR-003 幂等装载)直接复用,零额外机制。
2. **代理键只给真正需要它的 SCD2 维表**:`dim_shop` 的自然键 `(shop_id, platform)` 随版本重复,必须用 `shop_key AUTO_INCREMENT` 作主键。代理键**只新增、从不更新**,版本插入顺序由构建逻辑确定(同一次 diff 内有序),因此重放结果同样稳定。`dim_product` 虽是单版本最新态,仍给 `product_key` 预留代理键,便于未来快照轨扩展与 BI 侧 join。
3. **日期维用智能代理键** `date_key = YYYYMMDD`(确定性、免 join 即可推导日期)。
4. **stat_date 用 MySQL 生成列**:`dwd_orders.stat_date = DATE(COALESCE(created_at, updated_at))` 存储生成列(下单日,created_at 缺失时回退 updated_at),DWS 聚合与 BI 查询统一口径,且永不与事实列不一致。生成列由数据库维护,不进 upsert 列清单。

## 后果

- 优点:重放确定、装载机制统一、无代理键管理负担;生成列保证口径一致。
- 代价:未来若接入"同一 order_id 跨平台冲突"的数据源,自然键需加 platform 前缀——当前 `(shop_id, order_id)` 约定已含租户维度,单平台场景无冲突;真实平台接入时在适配器映射层兜底即可。
- 商品维"快照 + 最新态双轨"在 M4 只实现最新态轨(数据量小、全量重算成本可忽略),快照轨在真实平台接入后按需扩展(dim_product 已预留 product_key)。
