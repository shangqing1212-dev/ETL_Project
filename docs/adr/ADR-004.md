# ADR-004: Airflow 只做编排,ETL 逻辑沉淀在 SDK

- **状态**: 已接受
- **日期**: 2026-09-15

## 背景

两种典型反模式:(1) 把抽取/清洗逻辑堆在 DAG 文件里,难以脱离 Airflow 测试与复用;(2) 任务代码直接读写 Airflow metadata DB(在 Airflow 3 中已被硬性禁止,仅能通过 REST API)。

## 决策

- **SDK 边界**:所有 ETL 业务逻辑(适配器、抽取、装载、DQ、告警)在独立 pip 包 `etl_sdk` 中实现,与 Airflow 零依赖,可在本地 venv 用 pytest 直接测试。
- **Airflow 边界**:DAG 只做参数绑定、依赖声明、重试策略、调度周期。通过 `EtlTableOperator` 自定义 Operator 调用 SDK(入口由 entry_points 注册为插件)。
- **状态归属**:水位线、批次记录、DQ 结果、任务运行日志存放在自建 `etl_meta` 库,不依赖 Airflow 内部表(可随数仓一起备份、可独立迁移)。
- **解析期约束**(Airflow 3 硬约束):DAG 解析期禁止任何 DB 访问。店铺注册表读 YAML 文件;Airflow Connection/Variable 仅在任务运行时读取;凭据命名 `{platform}_{shop_id}`。

## 后果

- 优点:SDK 可单测/集成测试;换调度器(如未来迁 Dagster)业务逻辑零改动;符合 Airflow 3 架构约束。
- 代价:DAG 与 SDK 分属两个包,发版需同步 SDK 版本号到镜像构建(CI 中强制:镜像 tag 含 SDK git SHA)。
