# ADR-003: 水位线增量采用两阶段提交 + 重叠窗口

- **状态**: 已接受
- **日期**: 2026-09-15

## 背景

电商平台 API 普遍只支持按 updated_at 增量拉取,但存在两类问题:(1) 源端数据有**迟到更新**(记录晚于其 updated_at 进入可查询范围);(2) 若先推进水位、后写库,中途失败会造成**丢数据窗口**。

## 决策

1. **固定窗口**:批开始时刻计算 `window = [wm - overlap, wm_end)`,其中 `overlap = 1h`(覆盖迟到更新),`wm_end = now - 5min`(避开源端写入抖动)。`wm_end` 在批开始固定,批内绝不再取 "now"。
2. **两阶段提交**:全窗口抽取 → 批内去重 → 分批 upsert → DQ 检查全部通过后,才 `UPDATE etl_watermark SET watermark_value = wm_end`(带条件更新,防并发串扰)。
3. **失败不推进**:任何一步失败水位不动,重跑自动重读同窗口,upsert 幂等吸收重复。
4. **回填不推进**:`dag_run.run_type == "backfill"` 时窗口由 data_interval 显式给定,跳过水位读写。
5. **全量兜底**:`run_type=full` 时忽略水位,全量拉取后走"临时表 + RENAME TABLE"原子切换(ODS),或按 shop_id 分区 delete + reload。

## 后果

- 优点:重跑同窗口结果确定;迟到数据永不丢;实现简单可靠(比 binlog/CDC 适用面广,因为平台 API 通常不提供 CDC)。
- 代价:重叠窗口造成重复读取,由 upsert 吸收,是设计内成本;每批多拉 ~1h 数据。
