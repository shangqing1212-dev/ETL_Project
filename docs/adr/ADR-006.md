# ADR-006: 备份与监控策略 —— 逻辑备份 + 4 面板指标,不建第二套体系

- **状态**: 已接受
- **日期**: 2026-09-20

## 背景

M7 生产化需要确定两类策略:(1) MySQL 数据安全(备份/恢复);(2) 运行态监控。方案空间很大(物理备份 vs 逻辑备份、全链路监控平台 vs 自建),须按"单机 + 百万行/天 + 单店铺起步"的量级选**能演练、能看懂**的下限方案。

## 决策

1. **备份分层**:
   - 每日 `mysqldump` 逻辑备份(etl_meta + dw,保留 7 份)—— 恢复粒度到库,演练成本低;
   - binlog 开启(ROW 格式,保留 7 天)提供时点恢复(PITR)能力;
   - 生产每周 XtraBackup 物理全量(数据量增长到逻辑备份不可接受时启用,脚本化骨架随 deploy/ 提供);
   - **每月恢复演练**:scripts/backup_mysql.py → scripts/restore_mysql.py(drop + 重灌 + 行数校验),演练通过才算备份存在。
2. **监控只盯 4 个面板**(计划既定):DAG 成功率、任务时长 p95、DQ 失败数、批次延迟。
   - 指标源 = **etl_meta 单一事实源**(scripts/etl_metrics_exporter.py 输出 Prometheus 文本),
     不依赖 Airflow 内部 metrics/statsd 链路(3.x 的 statsd→Prometheus 需额外 exporter,多一跳);
   - 口径与数仓一致(批次成功率直接来自 etl_batch 状态),查询即 SQL,排障时人肉可复现;
   - Grafana 面板 provision 进 deploy/grafana/,4 面板固定不扩(有新增诉求先问"是否影响排障效率")。
3. **告警分层不变**:业务异常走 M3 AlertManager(钉钉/企微/邮件);Prometheus 侧不做告警规则,
   避免双轨通知;指标面板供值班巡检与事后分析。

## 后果

- 优点:备份可演练(每月一次,脚本化)、监控口径唯一且可人肉复现、不引入第二套告警与指标管线;
- 代价:逻辑备份在数据量大(千万行+)后耗时增长,届时按计划切 XtraBackup 周备;不做 PITR 演练
  (binlog 恢复为文档化手工流程,生产首次执行前须在演练环境验证一次)。
